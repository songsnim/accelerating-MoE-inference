EXP-004까지 GEMM 커널은 스레드 한 명이 출력 한 칸을 맡았다. 그 한 칸을 채우려면 곱셈 한 번마다 shared 메모리에서 숫자를 두 번 꺼내야 했다. GPU는 곱셈이 모자라서가 아니라 선반을 오가느라 놀고 있었다 — 피크 성능의 6%.

EXP-005는 스레드 한 명에게 4×4 = 16칸을 맡겼다. 선반에서 A 4개, B 4개 — 총 8개만 꺼내오면 그것들을 서로 곱해 16번의 곱셈을 할 수 있다. 곱셈 1회당 선반 방문이 2회에서 0.5회로, 4분의 1이 됐다.

스레드 수까지 세면 반전이 하나 있다. 두 블록이 k 한 칸에서 shared를 두드리는 총 횟수는 2048번으로 똑같다. AFTER는 스레드가 4분의 1(1024→256)이지만 스레드마다 8번씩 읽기 때문이다. 같은 양을 퍼가서 4배 많은 곱셈을 한다 — 그게 이 실험의 전부다.

왜 하필 4×4였나

타일 모양을 직접 바꿔보기

한 스레드가 맡는 칸을 늘릴수록 읽기 비율은 (TM+TN)/(TM×TN)로 떨어진다. 그러면 8×8은 왜 안 썼을까? 슬라이더를 움직여 보면 대가가 보인다 — 누적값을 담을 레지스터가 그만큼 필요해지고, 블록의 스레드 수가 줄어 점유율과 한 스레드가 감당할 적재량이 나빠진다.

왜 +1이 아니라 +4인가

shared 창구 32개

shared 메모리에는 창구(bank)가 32개 있고, float 주소를 32로 나눈 나머지가 창구 번호다. 한 워프의 32개 스레드가 서로 다른 창구로 가면 한 번에 끝나고, 같은 창구에 4명이 몰리면 4배 걸린다. 아래는 AFTER 커널이 A 타일을 전치해서 적재하는 순간(as[lc][lr])의 창구 배치다. 한 줄의 길이(stride)만 바꿔 보라.

한 줄의 길이

세 후보의 성적표

BEFORE 커널은 [32][33], 즉 +1로 충돌을 피했다. AFTER는 float4로 4개를 한 번에 읽어야 해서 줄 길이가 4의 배수여야 한다 — +1이라는 고전적 해법이 봉쇄된다. +4는 정렬을 지키면서 줄서기를 절반으로 줄이는 타협이다.

그런데 답은 한 비트도 안 변했다

안전망

부동소수점 덧셈은 순서를 바꾸면 결과가 달라진다. 타일 크기는 32에서 16으로 바뀌었지만, 출력 한 칸이 보는 k의 순서는 양쪽 모두 0, 1, 2, … 오름차순 그대로다. 더하는 식도 acc += a * b 그대로 — 컴파일러가 다른 형태의 FMA를 내지 않는다. 그래서 결과가 같을 수밖에 없다.

BEFORE · 타일 경계 32마다
AFTER · 타일 경계 16마다

경계(주황 선)는 달라졌지만 칸의 순서는 같다.

내부 루프 원문

// BEFORE — 읽기 2 : 곱셈 1 for (int i = 0; i < TILE; ++i) acc += as[ty][i] * bs[tx][i]; // AFTER — 읽기 8 : 곱셈 16 const float4 ar = *(float4*)&as[p][ty*TM]; // A 4개 const float4 br = *(float4*)&bs[p][tx*TN]; // B 4개 for (int i = 0; i < TM; ++i) for (int j = 0; j < TN; ++j) acc[i][j] += av4[i] * bv4[j];
