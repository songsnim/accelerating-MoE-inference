호출 지점

레이어마다 32회
- Tensor q, k, v; - layer.q_proj.forward(normed, q); // host matmul_transposed + to_device(d_in.get(), normed); // H2D 1회 + layer.q_proj.forward(d_in.get(), d_q.get(), total); + layer.k_proj.forward(d_in.get(), d_k.get(), total); + layer.v_proj.forward(d_in.get(), d_v.get(), total); + to_host(q, d_q.get()); to_host(k, ...); to_host(v, ...);

normed를 한 번 올려 세 개의 커널이 같이 씁니다. attention은 host에 남아 있으니 q/k/v는 다시 내려와야 하고, 그 결과 context가 또 올라가 o_proj를 거쳐 내려옵니다. 레이어당 국경 통과 6번. 이게 after의 새 비용입니다.

gemm_nt_bias · TILE × TILE 블록

EXP-002가 추가한 커널은 하나입니다. C[M,N] = A[M,K] · B[N,K]ᵀ + bias[N]. 스레드 하나가 C의 한 칸을 맡고, TILE×TILE 스레드가 한 shared memory 조각을 함께 읽어 TILE번 재사용합니다. 아래 값을 바꿔 보세요 — 시간은 전부 실측입니다.

shape
TILE
쓰는 칸 (C에 실제로 있는 출력)
버리는 칸 (M·N 밖 · 계산은 하고 결과는 던짐)
블록 경계 = TILE

for (int i = 0; i < TILE; ++i) acc += as[ty][i] * bs[tx][i]; // 워프 안에서 tx가 0..31로 다르다

실측

일하는 건 bs 쪽 패딩 하나입니다 — 없음 → bs만 2.77배. as[ty][i]는 워프 32개 스레드가 같은 주소를 읽어 broadcast로 끝나므로 패딩이 필요 없고, 붙이면 오히려 1.45배 손해입니다 (4 shape × 2 M에서 0.685~0.688로 일정). EXP-002 원문은 둘 다 붙였으니 as 쪽 1.45배를 그냥 내고 있습니다. GEMM이 0.5%였던 EXP-002에서는 무의미했지만, GEMM이 87%가 된 지금은 아닙니다.

as 패딩이 왜 느린지는 확인하지 않았습니다. stride 33이 128 B 정렬을 깨 넓은 로드를 막는 쪽이 유력하지만 SASS를 보지 않았으므로 추측입니다.

TILE만 바꾼 대조군

둘 다 패딩 vs 둘 다 없음: TILE=32에서 1.92배, TILE=16에서 1.10배. TILE=16은 워프 안에 tx가 0..15뿐이라 충돌이 32-way가 아니라 16-way입니다. 다만 충돌 횟수만으로 설명되는 격차보다 실측 격차가 작습니다 — 원인은 분리하지 않았습니다.
