MoE 프리필 최적화 로그

순차 CPU 코드로 주어진 MoE 추론의 프리필 구간을 4일 동안 13개의 실험으로 최적화한 기록이다. 각 실험은 가설 하나만 바꾸고, 출력이 직전 실험과 비트 단위로 같은지 확인하고, 그 결과가 다음 실험을 정한다. 아래는 그 순서와, 순서를 그렇게 정한 이유다.

EXP-000 기준선 0.0333seq/s n=1을 30.024 s에 처리. GPU 커널 0개.
EXP-013 현재 444seq/s n=1024 전량을 2.308 s에 처리.
누적 배수 13,300× 기준선은 n=1, 현재는 n=1024라 배치 이득이 포함된 값이다.
정확도 1.79e-4 max abs diff. 임계값 3e-3의 6%. EXP-005 이후 한 번도 변하지 않았다.
01 — 무대

무엇을, 어디까지 건드릴 수 있는가

02 — 규칙

이 로그를 읽을 때 전제되는 네 가지

숫자보다 이 네 가지가 먼저다. 여기 어긋난 측정은 이 프로젝트에서 증거로 치지 않는다.

RULE 1

실험 하나에 가설 하나

EXP-001은 배치화와 attention 재작성을 한 커밋에 섞었다. 어느 쪽이 레버인지 몰라 나중에 가르는 빌드를 따로 만들어 다시 재야 했다 — 배치화 1.59× × attention 1.82×. 큰 쪽은 attention이었고, 원래 기록은 틀려 있었다.

RULE 2

cmp가 안전망이다

성능 실험은 매번 직전 실험의 출력과 바이트 단위로 비교한다. 동일하면 누적 순서를 건드리지 않았다는 증명이고, 다르면 그 이유를 설명할 수 있어야 한다. 기준은 host 코드가 아니라 직전 실험 출력이다 — EXP-002에서 이미 갈라졌다.

RULE 3

A/B는 한 srun 안에서 교차로

노드 b1은 b5/b6보다 1.19× 느리다. EXP-007을 서로 다른 노드에서 재고 1.04× 이득이라 착각했다가, 교차 측정하니 0.99× 회귀였다. 몇 % 짜리 효과는 교차 측정 없이는 측정 자체가 불가능하다.

RULE 4

추측 금지, 계측

APS_PROFILE=1 단계 타이머, nsys 커널 분해, ncu 점유율·섹터, objdump로 host SASS 확인까지. EXP-002의 가설이 빗나간 것도, EXP-008의 메커니즘이 틀린 것도 전부 계측이 잡아냈다.

03 — 지뢰

왜 비트 단위 동일성이 협상 대상이 아닌가

이 프로젝트에서 가장 비싼 교훈. EXP-004에서 layer_norm을 평범한 block tree reduction으로 짰더니 n=8은 통과하는데 n=1024가 터졌다.

FAILURE MODE · 라우터 양자화 경계
tree reduction
합산 순서 변경 → router logit
~1e-7 흔들림 → ROUTER_SCORE_QUANTUM
양자화 + tie-eps → 선택된 expert
집합이 뒤집힘 → 해당 토큰 출력
O(0.1) 오차

증상은 max abs diff 0.211975인데 mean 6.83e-05. 1,024개 중 4개 시퀀스만 터졌다. 평균은 그대로인데 최대값만 튄다는 것은 정밀도 문제가 아니라 이산적 결정이 뒤집혔다는 신호다. 634k번의 라우팅 결정 중 몇 개면 충분하다. (top-1/top-2 순서만 바뀌는 것은 가중치가 둘 다 0.5라 무해하다. 집합이 바뀔 때만 터진다.)

그래서 이후 모든 커널은 host와 비트 단위로 같게 설계한다. objdump obj/tensor.o로 host가 실제로 무엇을 내는지 먼저 확인했다 — vaddss 단일 accumulator 순차 누적, 벡터화도 FMA도 없다.

  • 누적은 host와 같은 순서로 직렬. 필요하면 thread 0이 혼자 두 번 훑는다 (직렬화 비용 1.2%).
  • __fadd_rn / __fsub_rn / __fmul_rn으로 nvcc의 FMA contraction을 차단. host가 안 내는 FMA를 device가 내면 결과가 달라진다.
  • rsqrtf 금지 — 저정밀 근사다. 1.0f/sqrtf(...)만 쓴다.
  • RoPE의 cos/sin 테이블은 host에서 계산해 8 KB만 업로드. device powf/cosf는 glibc와 1 ulp 다를 수 있고, 그 1e-7이 정확히 라우팅을 뒤집는 크기다.

반대로 안전하다고 증명된 것도 있다. 타일 shape 변경, double buffering, register tiling, W1/W3 융합, grouping — 출력 원소별 k 누적 순서를 건드리지 않으므로 전부 비트 동일이었다. 구조는 자유롭게 바꿔도 되고, 순서만 지키면 된다.

04 — 지도

병목은 여섯 번 이동했다

이 프로젝트의 전체 서사는 한 문장이다: 가장 큰 항목을 없애면 병목이 다음 항목으로 옮겨간다. 어느 실험도 "전반적으로 빠르게" 하지 않았다. 매번 프로파일의 1등 항목 하나만 겨눴다.

n=1024 전체 실행 시간 로그 스케일. EXP-000~002는 n=1024를 2분 안에 끝내지 못해 이 축에 없다. 노드 배지는 측정 노드 — b1은 b5/b6보다 약 1.19× 느리므로 서로 다른 배지의 값은 직접 비교하지 말 것. EXP-008의 막대가 EXP-006보다 긴 것은 퇴행이 아니라 느린 노드(b1)에서 잰 값이기 때문이다. 오른쪽 배수는 같은 노드 안에서 직전 실험과 교차 측정한 값만 표시했다.
단계별 시간 구성비 APS_PROFILE=1 단계 타이머를 각 마일스톤의 프로파일 합계로 정규화했다. 8% 미만 구간은 라벨을 생략했다 — 정확한 초 단위 값은 아래 표에 있다. EXP-003의 프로파일 합계(57.3 s)가 실측 elapsed(48.8 s)보다 큰 것은 계측용 sync가 추가되기 때문이다. EXP-011의 PCIe 값만 추정치다 — 그 실험은 h2d/d2h를 따로 찍지 않아 EXP-012b의 실측 h2d(0.031 s)에 router d2h(≈0.006 s)를 더했다.

기준선 — 코드 무수정

EXP-001채택

배치화 — 전 토큰을 [T, 4096] 한 행렬로

가설 19,803개 토큰을 하나로 연결해 32 레이어를 한 번만 통과시키면 가중치를 레이어당 1회만 읽고, matmul의 M이 19 → 19,803이 되어 OpenMP 병렬화가 살아난다. layer_norm·matmul·silu·MoE 라우팅은 전부 행 단위 독립이라 연산 순서가 바뀌지 않는다.
결과 2.88× (n=2 기준). 출력 bitwise 동일 — 배치화가 부동소수점 순서를 전혀 바꾸지 않았음이 증명됐다.
배운 것 가설 두 개를 섞은 대가로 나중에 가르는 빌드를 만들어야 했다: 배치화 1.59× × attention 재작성 1.82×. 큰 쪽은 attention이었다.
그리고 진짜 벽을 찾았다 — matmul_transposed는 shape와 무관하게 1.2 GMAC/s에 고정이다. 이 경로로 20.4 TMAC을 돌리면 1.2시간이 걸린다.

EXP-002채택

q/k/v/o + lm_head를 자체 CUDA GEMM으로

가설 전체 연산의 66%인 projection을 GPU로 옮기면 사실상 공짜가 되어 2.5× 이상. (Amdahl 상한 1/0.34 = 2.9×)
한 일 shared-memory tiled GEMM gemm_nt_bias 커널 1개. 가중치는 생성자에서 device로 올리고 host 사본은 즉시 폐기(host RAM 2.7 GB 절약). bias는 커널에 융합.
결과 1.69×. 가설은 틀렸다. 프로파일을 보니 moe 28.007 / 28.55 s = 98.1%, GPU로 옮긴 GEMM 전체는 0.153 s에 끝난다.
배운 것 비중을 FLOP으로 추정한 것이 틀렸다. MoE의 비용은 연산량(34%)이 아니라 토큰마다 Tensor를 새로 할당하고 at()으로 원소 단위 gather/scatter를 하는 데 있었다. 이후로는 비중을 반드시 프로파일로 잡는다.

EXP-005채택

register-tiled GEMM — 스레드당 4×4 출력

가설 GEMM이 피크의 6%에 머무는 것은 FLOP이 아니라 shared 대역폭에 막힌 신호다. 스레드당 출력을 1개 → 4×4로 올리면 MAC당 shared 읽기가 2회 → 0.5회로 4배 줄어든다.
한 일 BM=BN=64, BK=16, TM=TN=4. shared를 k-major로 전치 저장하고 +4 패딩으로 16 B 정렬을 유지한 채 bank conflict를 깼다 (float4 shared 로드의 필수 조건이라 +1은 못 쓴다).
결과 3.77× — 가설(2.5~3×)을 넘겼다. 실효 성능 2.0 → 15.7 TF/s, 피크의 6% → 44%. shared bound 진단이 맞았다.
배운 것 출력당 accumulator 1개 + k 오름차순만 지키면 타일 shape는 정확도 리스크가 없다. 이후 타일 실험을 자유롭게 할 수 있게 된 근거다.

EXP-007롤백

register tile 4×4 → 8×8

가설 타일을 128×128, BK=8, TM=TN=8로 키우면 shared load 1회당 FMA가 2 → 4가 되어 peak 43.6% → 60%+.
결과 가설은 절반만 맞았고 전체로는 반증됐다. wide-N GEMM(q/k/v/o)은 1.17×(−0.302 s)인데 narrow-N expert GEMM은 0.81×(+0.341 s). 순효과 −0.8% 회귀 → 롤백.
배운 것 expert w1/w3(M~2475, N=448)의 블록이 273개 → 80개로 붕괴한다. 82 SM에 80블록이면 SM당 1블록 = 8 warp(최대 48) → latency hiding이 죽는다. N 패딩 낭비 12.5%만으로는 설명되지 않으므로 점유율이 주범이다.
반증이 아니라 분기 지점이다 — 두 호출 지점이 서로 다른 타일 shape를 원한다는 것이 이 실험의 실측 결론이고, 이후 EXP-008/010/012가 전부 여기서 갈라져 나온다.

EXP-008채택

shared double buffering

가설 K 루프가 LDG → STS → sync → compute → sync 구조라 매 반복 글로벌 로드에서 멈춘다. shared를 2중 버퍼로 두면 다음 타일 로드가 현재 compute에 가려진다.
결과 전체 1.041×, wide GEMM 1.28× (15.5 → 19.9 TF/s, 피크의 55.9%).
배운 것 가설은 맞았지만 메커니즘은 틀렸다. SASS를 보니 ptxas가 LDG를 compute 뒤로 sink시켰다 — 레지스터 127개로 2 blocks/SM 경계에 붙어 있어 지연 은닉은 실패했다. 실제로 작동한 것은 반복당 BAR.SYNC 2회 → 1회뿐이다. 결과가 맞아도 이유를 확인해야 다음 실험을 제대로 고를 수 있다.
ncu feature-major 전환 불필요 확정 — sectors/request 14.5~15.8(이상값 16의 90~99%), dram throughput 3.7~10.8%. 메모리 경로에 고칠 것이 없다.
대신 expert GEMM의 두 손실을 지목했다: 164 슬롯 중 40~72만 채우는 블록 붕괴와 N=448에 BN=128이라 생기는 12.5% 패딩 낭비.

wide GEMM1.719 → 1.341 s

EXP-009채택

softmax의 FP64 exp를 lane에 분산

배경 외부 조사 문서가 2등 참가자의 "Attention Q-head 4-way(3.49×)"를 최우선으로 권했다. 그러나 그 설계는 우리 코드에 이식되지 않는다 — 저쪽은 block이 GQA group 하나를 맡아 thread 0이 q head 4개를 연달아 계산했고, 우리는 block = (시퀀스, q head)라 이미 별도 block에서 병렬이다. 저쪽이 추가한 병렬성을 우리는 이미 갖고 있으므로 배수가 전이되지 않는다.
한 일 직렬 구간을 셋으로 쪼갰다: tid 0이 max 스캔 → 128 lane이 exp(sw[i]-max)를 나눠 계산 → tid 0이 denom을 ki 오름차순으로 직렬 누적. exp는 elementwise라 어떤 합산 순서도 건드리지 않는다.
배운 것 대조군으로 직렬 구간을 통째로 삭제한 진단용 하한(0.178 s, 결과는 오답)을 같이 재서, 이 변경이 가용 여유의 96%를 회수했음을 1회 측정으로 확정했다. Q-head 4-way를 완벽히 해내도 상한이 0.113 s다 — 이 방향은 여기서 닫혔다.
남의 최적화는 배수가 아니라 메커니즘을 보고 우리 구조에 남아 있는지 확인해야 한다.

speedup1.59×

EXP-011채택

Prefix trie — 공유 prefix 중복 제거

가설 causal attention + 절대위치 RoPE이므로, 앞선 토큰이 전부 같은 두 토큰은 32개 레이어 전부에서 동일한 hidden state를 갖는다. 행을 토큰이 아니라 prefix trie 노드로 잡으면 공유 prefix를 1번만 계산한다. 정확히 CSE — 산술 변경 0.
실측: 19,803 토큰 → 15,583 노드 (−21.3%).
한 일 각 노드의 key 집합 = 자기 root path를 depth 오름차순으로 평탄화(863 KB)해 attention이 parent 체인을 되짚지 않게 했다. attention block을 (시퀀스, head) → (노드, head)로 바꾸고 position은 trie depth를 쓴다.
배운 것 행 수에 비례하는 항목은 전부 −21% 근처로 떨어졌는데 attn만 −24.7%로 예상(−6.5%)을 크게 넘겼다. qi 직렬 루프가 사라져 블록이 16,384개 → 249,328개로 펴진 병렬성 효과다.
그리고 expert당 행이 줄어 w13 충전율은 더 나빠졌다 — grouping의 상대 가치가 올라갔다.

EXP-012채택

expert GEMM grouping — 16개 launch를 1개로

한 일 16개 expert의 행을 한 버퍼에 이어 붙이고 (expert, rowtile) work queue로 평탄화했다(레이어당 ~250 타일). gather도 16회 → 1회. scatter만 expert별로 유지 — 한 행이 expert 2개에 속하므로 launch를 나누는 것이 두 add의 경쟁을 막는 방법이다.
결과 moe 1.26× — 예측(−0.19 s)과 정확히 맞았다. 충전율 가설이 옳았다.
단, 코드가 바뀌지 않은 gemm 구간이 +0.023 s 퇴행했다(2rep 재현).
기록 원칙 퇴행의 원인을 그 자리에서 추측하지 않고 "미해결"로 남겼다. 바로 다음 측정-B가 그것만 파고들었다.

측정-B측정만

gemm 퇴행의 원인 — 후보를 하나씩 죽였다

버퍼 크기? 아니다. EXP-011에 할당만 똑같이 +650 MB 키운 011big을 만들어 3-way 교차 → gemm 그대로. 계획했던 "버퍼를 줄여 되돌린다" 실험이 여기서 소멸했다.
리팩터링? 아니다. 경계 표현을 원본과 문자 단위로 되돌려 gemm_nt_bias의 SASS를 EXP-011과 완전히 동일하게 만든 012b도 퇴행이 그대로였다.
원인 boost 클럭이다. grouped MoE는 같은 FLOP을 0.98 s → 0.78 s에 밀어넣으므로 전력 밀도가 26% 높다. GPU가 boost를 한 단 내리고 (1800 → 1755 MHz, −2.5%), 그 손해를 뒤이은 projection과 attention이 가져간다(+2.4%, +2.9%). 메모리 바운드 단계(norm·resid·h2d·d2h)는 ms 단위로 불변이다. 이미 클럭이 낮은 b1에서는 퇴행이 아예 없다.
앞으로 코드로 되돌릴 수 없는 물리적 트레이드오프다. 연산 밀도를 올리는 최적화는 빠른 노드에서 이론치의 97~98%로 기대값을 잡는다.
EXP-013채택

embedding lookup을 device로

계획 변경 다음 순서였던 Q/O cp.async가 구조적으로 막혀 있다: 타일이 as[BK][BM]로 전치되어 있는데 cp.async는 global→shared 연속 복사만 된다. 전치를 버리면 내부 루프가 LDS.128 ×4 → LDS.32 ×16이 되어 손해다. 타일 재설계급이라 보류.
한 일 대신 남은 최대 단일 항목이 전부 호스트 직렬 코드였다 — 15,583행 × 16 KB = 255 MB를 CPU 1스레드로 모으고 다시 255 MB를 업로드. 임베딩 테이블(525 MB)을 다른 가중치와 똑같이 로드 시점에 device로 올리고 기존 gather_rows를 재사용했다. 순수 복사라 산술 위험 0.
배운 것 −0.23 s로 예측(−0.19)을 넘겼고, 다른 단계는 ms 단위로 불변이었다 — 측정-B의 클럭 효과가 없다. 임베딩 gather는 메모리 바운드라 전력 밀도를 올리지 않기 때문이고, 이는 "컴퓨트 바운드 단계만 클럭 손해를 본다"는 결론과 일관된다.
부수적으로 trie 구성 자체는 2 ms로 확정됐다.
